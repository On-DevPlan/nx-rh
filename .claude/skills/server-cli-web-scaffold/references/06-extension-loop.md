# 06 · 扩展闭环：给已有项目加一个功能域

> 归属主文档 [[server-cli-web-scaffold]] 的「扩展闭环」路由。本文件是新增/修改一个功能域时的完整落点清单与验收判定。

## 一、什么时候读这个

- 要给一个**已经跑起来**的 server-cli-web 项目加一个新功能域（`src/modules/<域>/`）
- 要改一个已有功能域的**对外面**（加命令、加路由、改参数、改返回形状）
- 代码写完了，要确认「三端同源」这一次也没漏

不适用：从零建项目——那是主文档「创建流程」阶段 1–6 的事。

**为什么单独成文**：主文档的三条核心不变量讲的是「为什么这样设计」，
本文件讲的是「改一次代码，实际要动手碰哪几个文件，漏了哪一个会怎样」。
这是两种不同的信息，混在一起会让主文档既像原理又像清单。

## 二、闭环：一次改动要落到这几处

以新增功能域 `X` 为例。**每一处都有「漏了会怎样」——多数是静默失效，这才是要列出来的原因。**

| # | 落点 | 漏了会怎样 | 谁会发现 |
| --- | --- | --- | --- |
| 1 | `src/modules/X/service.js` | — （业务本身） | — |
| 2 | `src/modules/X/index.js` | 命令不存在 | 装载期自检 / 一致性测试 |
| 3 | `src/modules/X/view.jsx` | 有 view 声明却没文件 → **构建期报错** | `vite build` |
| 4 | `src/runtime/registry.js` 的 `MODULES` | 模块整个不生效，命令与路由都不存在 | 一致性测试（目录 ↔ 注册表对账） |
| 5 | `src/web/frontend/registry.js` 的 `VIEWS` | 后端有 view、前端无 tab | 一致性测试（两侧视图表对账） |
| 6 | `src/index.js` 的 `export * as X` | 库用方拿不到该 service | ❗**无任何断言**，纯静默 |
| 7 | `eslint.config.js` 的互依禁列加 `../X/*` | 别的模块可以随意 import 它，分层规则对新模块失效 | ❗**无任何断言**，纯静默 |
| 8 | `core/paths.js` 新增常量（如有） | 散落的字面量路径 | 无断言，靠 review |
| 9 | `tests/unit/` 纯逻辑测试 | 算法只被端到端测试覆盖，CI 上跑不了（平台相关时） | 无断言，靠自律 |
| 10 | `tests/smoke.mjs` 只读断言 | 端到端坏了没人知道 | 无断言 |
| 11 | **`assets/<skill>/` agent 文档** | agent 永远不知道这条命令存在 | ❗**单向断言**，见第三节 |
| 12 | `README.md` 命令总表 / `CHANGELOG.md` | 文档与实际脱节 | 无断言 |

**读法**：第 4、5 两处有测试兜底，漏了会红；第 6、7、11 处**没有任何东西会告诉你**，
必须靠这张表逐条对。

## 三、最容易漏的三处（都实测踩过）

### 1. eslint 的模块互依禁列是**逐模块枚举**的

分层规则通常这么写：

```js
group: ['../repos/*', '../skills/*', '../github/*', '../bundled/*', '../system/*']
```

它是**白纸黑字的枚举**，不是通配。于是新增一个 `env` 模块时，如果忘了往这行里补
`'../env/*'`——**不报错，也没有任何测试会红**。后果是新模块悄悄变成「谁都可以依赖」，
而这条规则随模块数增加持续衰减：加了五个模块、漏了三次，规则就废了一半。

**正确做法**：把「加模块时必须补禁列」写进本文件的闭环表（已写，第 7 项），
并在禁列旁边留一句注释说明它是枚举式的、漏补是静默的。

> 更彻底的做法是用「默认拒绝 + 白名单」表达（禁列写成 `../*\/*` 再逐个放开，
> 或让每个模块在自己的 `index.js` 里声明依赖），但改动量大。若项目模块数会长期增长，
> 值得一次做掉；否则靠这张表盯着。

### 2. 读命令上的 flag 不要写 `default`

这是本次实测逮到的一个隐蔽 bug，破坏力很大：

```js
// ✗ 看起来无害，实际让 env list 的「合并视图」永远出不来
flags: { scope: { type: 'string', enum: ['user','system'], default: 'user' } }
```

参数强转层会把 `default` **无条件注入** ctx。于是 `list()` 里那个
「没传 scope 时合并两个 scope」的分支**永远走不到**——命令不报错、不崩，
只是永远返回单 scope 的半个结果。

**规则**：

- **写命令**（`set` / `remove` / `add`）的 `scope` / `mode` 这类 flag 该有 default——缺省要有个合理归属
- **读命令**（`list` / `get`）的同名 flag **不能有 default**——「没传」本身就是一种有意义的输入，
  通常代表「全部 / 合并」。要保留这个语义差，就不要给它填默认值。

**自检**：写完一条读命令，问「不传这个 flag 时我想要的是哪个分支」，然后确认那条分支真的可达。

### 3. 文档漂移防护是**单向**的

常见的断言长这样：

```js
// 文档里提到的每条命令都必须真实存在
assert.deepEqual(problems, [], '文档里的这些命令解析不到');
```

它只保证「文档 → 代码」这一个方向。**反方向（代码 → 文档）通常不强制**，
理由也合理：不是每条内部命令都值得写进 agent 手册。

后果：**给项目加了一条新命令而忘记写进 `assets/<skill>/`，没有任何测试会红。**
而这条命令对 agent 来说等于不存在——它能用的只有文档里写过的那些。

**正确做法**：把「更新 `assets/<skill>/`」当成闭环表里的**必做项**（第 11 项），
而不是「有空再补」。判断标准很简单：

> 这条新命令，agent 会在什么场景下需要它？如果有答案，它就必须出现在 agent 手册里。

## 四、让「漏了」变成红灯

闭环表里带断言的那几项，是**用机制替代记忆**的地方，值得先确认它们真的会在项目上触发：

| 闸 | 拦什么 | 怎么确认它真的会触发 |
| --- | --- | --- |
| 装载期自检 | 重复的 action id / CLI 路径 / HTTP 路由；action 缺 `cli`；`http` 既不是数组也不是 `null` | 故意加一条重复命令，确认启动即抛错 |
| 模块目录 ↔ 注册表对账 | 写了模块目录却忘了登记（反之亦然） | 建一个空模块目录，跑单测看是否报「没有登记」 |
| 后端模块 ↔ 前端视图对账 | 有 view 却没登记 tab、或登记了不存在的视图 | 删掉前端注册表里某一行，跑单测 |
| 视图里的 `/api` 字面量 | 面板调了一个不存在的端点 | 把某个 `api('/api/x')` 改成不存在的路径，跑单测 |
| CLI 路径可解析回自身 | 命令匹配算法被改坏（别名竞争、最长匹配失效） | 靠既有断言即可 |
| lint 分层 | 越层 import、前端 import 了 `node:` 模块、模块互依 | **必须做一次反向测试**：临时写一个违例文件，确认 lint 退出码非 0 —— 验证规则本身是否生效和验证代码是否合规是两件事 |

最后一条特别值得做：**lint 规则写错了不会报错，只会永远通过。**
一个从来没红过的规则，和一个不存在的规则是一样的。

## 五、正反例

**正例（本仓库新增 `env` 模块时的实际落点）**：

```
src/core/envvars.js              平台驱动（core 层，不 import 上层）
src/modules/env/service.js       业务 + 安全网（破坏性操作的全部守卫）
src/modules/env/index.js         11 条 action
src/modules/env/view.jsx         面板
src/runtime/registry.js          + import env，MODULES 加一项
src/web/frontend/registry.js     + VIEWS 一行
src/index.js                     + export * as env
eslint.config.js                 + '../env/*' 进互依禁列
tests/unit/envvars.test.mjs      纯逻辑断言（CI 能跑）
tests/smoke.mjs                  + 只读与 dry-run 断言
assets/repo-hub/references/env-manage.md   + 路由表一行 + 主文档场景一行
README.md / CHANGELOG.md         命令总表与变更记录
```

**反例**：

| 做法 | 后果 |
| --- | --- |
| 「先加命令，文档回头补」 | 回头是永远。agent 侧这条命令等于不存在，而没有任何测试会提醒 |
| 新模块只登记了 `runtime/registry.js`，忘了前端 `VIEWS` | 后端报「模块有 view 但前端没登记」，一致性测试在 CI 上红——这次是**会红**的，属于幸运的一类 |
| 新模块忘了进互依禁列 | 静默。半年后没人说得清哪些模块允许互相依赖 |
| 读命令的 flag 照抄写命令的 `default` | 命令不报错、返回半个结果。调用方以为「全部」拿到的是「一部分」 |
| 改完只跑 `pnpm build` | 构建只管前端能不能编译，命令表/路由表/视图表三张表的一致性它一概不管 |

## 六、验收清单（交付前逐条勾）

- [ ] 新模块目录已登记进 `runtime/registry.js` 的 `MODULES`
- [ ] 有 `view.jsx` 的模块已登记进 `web/frontend/registry.js` 的 `VIEWS`
- [ ] `src/index.js` 已导出新 service（**无断言，靠这条**）
- [ ] `eslint.config.js` 互依禁列已加 `../<新模块>/*`（**无断言，靠这条**）
- [ ] 读写命令的 flag 语义已区分：写命令可带 `default`，读命令不带
- [ ] 破坏性操作（改系统状态 / 删文件 / 覆盖内容）**每条写命令都有 `--dry-run`**，
      且写前自动留可回滚的快照
- [ ] 纯逻辑已下沉成不依赖平台的函数，并有 `tests/unit/` 断言（这样 CI 上跑得起来）
- [ ] 冒烟测试覆盖了新命令的**只读路径**；破坏性路径用 `--dry-run` 覆盖，**绝不真写**
- [ ] `assets/<skill>/` 的 agent 手册已加新场景，并在其路由表登记「何时读取」
- [ ] `README.md` 命令总表已补，`CHANGELOG.md` 已记
- [ ] 全链通过：`pnpm test`（lint + build + 冒烟 + 单测），而不是只跑 build
